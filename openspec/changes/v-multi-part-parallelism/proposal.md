# Phase V - Multi-part parallelism (per-part render/slice/pack on independent worker threads; Solids stay thread-local, mesh data crosses)

## Why

A multi-part model's per-part geometry runs one part at a time on one kernel thread. The GUI's geometry service launches a single shard, auto-plan walks the parts one by one and the co-pack layout waits on each part in turn. The CLI's `fab slice` loops over the parts serially too. Once T.2b splits a model, its parts are independent, so this phase spreads the per-part work across worker threads. The `!Send` `Solid` never leaves the thread that owns it, and only mesh data moves between threads.

## What Changes

- Nothing has shipped under V. V.1 is the only box, open since `4ef936ff` (2026-07-12). No commit subject or code comment cites it. The one later mention is O.10's close (`b0844f81`, `docs/models-profile.md:856`): it left the next profile to choose between an O.11 band and V.1. No later profile chose between them (no O.11 exists), and AR.21 (`32a04b7e`) retired the hand-written intrinsic tier an O.11 band would have extended. The nearest number is AR.0's split (`aaffa2df`: median 60% eval over 50 models, pre-transpiler), which caps what parallel lowering wins on a render; the per-part read-ops sit outside it.
- Already built is the seam, not the parallelism. W.3.3 (`006b17b1`, `e6bea696`, `1ac6c635`) put sharding into the types: `SolidId.shard` (`src/geomsg.rs:71`), read-ops routed by `base.shard` (`gui/src/geom.rs:82-91`) and `GeomPool::new(n)`. It launched N=1 at all three call sites (`gui/src/lib.rs:222,484,556`). `docs/geometry-service.md:85-86` calls raising N "a config change". It isn't one, because four things are missing:
  - **Mints:** `RenderParts` evaluates once and mints every part into the store of the shard that ran it (`src/geomsvc.rs:644-651`). No request mints a part from mesh data on a different shard, so spreading parts across shards needs a new arm or a hand-off at the pool level. That hand-off is the "mesh data crosses" half of the title.
  - **Routing:** `Free` routes by its first id only (`geom.rs:88`), and `free_bases` sends every part's base in one `Free` (`gui/src/jobs.rs:1159`), so a batch that spans shards strands every handle off the first one's shard. `SaveMeshes { base }` falls through to `_ => 0` (`geom.rs:89`), which stays latent while its only input, a `RenderWhole` handle, is minted on shard 0. Both should route on their ids.
  - **Callers:** auto-plan is single-slot and does one part at a time (`gui/src/jobs.rs:2144-2221`), and it runs on the desktop only (`lib.rs:46`). The print layout awaits each part's `PrintLayout` in a serial loop (`gui/src/print.rs:119-150`). Reslice touches only the active part, behind the single `Job` slot (`jobs.rs:172`). Raising N alone parallelizes none of these.
  - **CLI and web:** `slice_model_parts` slices parts in a serial loop (`src/slicing.rs:188-207`), and `fab make` never splits parts at all (`src/auto.rs:184` renders one whole `Solid`). On wasm, `GeomPool` is a zero-sized type over one Worker and ignores `n` (`gui/src/geom_wasm.rs:144-150`). Each Worker starts a rayon pool with `navigator.hardwareConcurrency` threads (`packaging/web/geom-worker.js:26`), so N Workers means N times the threads on the same cores and N times the wasm memory.
- Design tension the box doesn't name: evaluation is one pass over the whole program, so "render each part on its own thread" can only parallelize the lowering. That lowering deliberately shares ONE memo across all parts, because a sliced model shares its base subtree between parts (`src/backend.rs:205-206`). The X.1 cross-render cache is also per store (`geomsvc.rs:37-40`; `SPEC.md:395`). Lowering on separate threads gives up both. The shape that keeps both is to render on one shard, then fan the per-part read-ops (AutoPlan, PrintLayout, Reslice) out to shards that receive the parts as mesh data.
- The title's premise still holds, for a different reason. `Solid` is still `!Send` by construction (`src/kernel.rs:86-102`, pinned by a `compile_fail` doctest). The C++ race that forced it is gone since M.7.4 (`kernel.rs:91-93`), so the marker is now a guardrail. `SPEC_manifold-rs.md:215` (OPEN #3, "Do we WANT `Solid: Send`?") is still undecided. An `Arc`-backed `Solid` would let one render hand its parts to other threads without copying the mesh. V.1 is the first open work where the answer has a price (a mesh copy per crossing), and it can proceed under `!Send` and leave OPEN #3 open.
- "pack" in the title is stale. Packing is ONE co-pack across every part's pieces (T.2b.4, `ef0ce1b9`; `src/slicing.rs:211-218`). Only print-layout (the per-part orient) is per-part, and that is what V.1's own text names.
- Byte determinism under concurrent ops is untested. The mesh-instance id counter is process-global (`manifold/src/mesh.rs:31`), and its comment claims only id equality matters (`mesh.rs:27-30`). The absolute-value half is covered: `tests/determinism_render.rs` renders N times in one process on purpose, and S.4's audit found the ids never reach bytes. The C++ counter it replaces was flagged as handing out ids in a nondeterministic order across shard-pool ops (`docs/tbb-backend-spike.md:33-34`), and nothing checks bytes while two kernel ops reserve ids at once: no manifold test spawns a thread, CI's nextest runs each test in its own process, and the 12-wide in-process `tests/bosl2_examples.rs` sweep is `#[ignore]`d and checks only genus and sym-diff. V.1 would be the first deliberate test. Mesh data crossing shards or Workers needs no re-mint step, since `from_mesh_gl` lands it as a fresh original (`mesh.rs:663`) on native and wasm alike. What it loses is the render's `tri_ref` provenance, and nobody has checked whether the downstream reslice and print-layout booleans need it.
- No measurement says V.1 pays. `geometry-service.md:165-171` said to measure the reactive loop in dogfooding and expected contention to be rare. No measurement of shard contention exists in `docs/` or `perf/`. The native kernel already runs `par` inside each op. The only per-part parallel map in the tree, `decimate_parts` (`src/decimate.rs:487`, `b352accc`), has never had a production caller.
- V then reduces to V.1, which really holds five steps: a contention measurement on a real multi-part model, the `SaveMeshes`/`Free` routing fix, a mint-from-mesh arm, concurrent auto-plan and print-layout callers on native, and then a web Worker pool sized against each Worker's own rayon pool.

## Impact

- Transport: `gui/src/geom.rs` (`GeomPool`, `shard_for`, the shard thread), `gui/src/geom_wasm.rs` (the single-Worker pool), the three `GeomPool::new(1)` sites in `gui/src/lib.rs`, and `packaging/web/geom-worker.js` (the rayon pool in each Worker).
- Callers: `gui/src/jobs.rs` (`kick_auto_plan`'s single-slot `AutoJob`, `auto_reslice`), the `Job` slot (`gui/src/state.rs:172`), `gui/src/print.rs` (`kick_print_job`'s serial loop) and `src/slicing.rs` (`slice_model_parts`).
- Service and kernel: `src/geomsg.rs` (`SolidId`, `Request`, where a mint-from-mesh arm would go), `src/geomsvc.rs` (`SolidStore`, `render_parts_svc`, the per-store `geo_cache`), `src/backend.rs` (`build_geo_parts`'s shared memo), `src/kernel.rs` (the `!Send` marker) and `manifold/src/mesh.rs` (`MESH_ID_COUNTER`).
- Tests that guard the serial path today: `pool_renders_reslices_off_the_held_handle_then_frees` (`gui/src/geom.rs:113`, N=1 only), `render_mints_a_handle_reused_by_reslice_then_freed` (`src/geomsvc.rs:1139`), `build_geo_parts_splits_top_level_items` (`src/backend.rs:1525`), `slice_model_parts_cuts_the_bound_part_and_keeps_the_rest_whole` (`src/slicing.rs:742`) and the byte goldens (`manifold/tests/m6_native_wasm_golden.rs`, `m7_golden_mode.rs`). No CI-gated test runs N>1 or concurrent kernel calls. `manifold/tests/par_speedup.rs` (W.6.2) is the template for the measurement.
- Owning doc: `docs/geometry-service.md` (Sharding and Known tradeoff). At least four passages are stale: the `i % N` mint policy at :83-84 (one render mints into one store), the "config change" line at :85-86 and its echo at :169, the TBB framing at :87-88, and the crash model at :138-141, which still names C++ traps (as do `gui/src/geom.rs:8-10` and `geom_wasm.rs:5-6`). Cache placement lives in `SPEC.md` X.1 and the `Solid: Send` question in `SPEC_manifold-rs.md` OPEN #3.
- Release reach: CI on every push. A v* tag ships it in both the desktop app and the web bundle. The `geomsg` protocol is internal to one build (the GUI and the geom worker ship together), so a new request arm creates no compatibility problem between versions. hotchkiss.io keeps serving v1.3.2's bundle (its `build.rs:33`) until its own pin moves. There is no one-way door: nothing persisted changes, and nothing touches `latest.json` or the signing key.
- External: browser thread and memory budgets under COOP/COEP. No OpenSCAD or BOSL2 pin is involved.
