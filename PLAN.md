## Phase AO - Generated-model PERF differential vs OpenSCAD (the heavy lane — today's corpus is too trivial to time)
- [x] AO.1 - Parameterize the generator's bounds into a Profile — `cheap` (today's gen-diff constants, unchanged bit-for-bit) vs `heavy` (dialed); same seed replays deterministically per profile
- [x] AO.2 - Generate the heavy lane from a DECLARED SURFACE, not a hardcoded grammar. The content is still geometry-weighted (high-$fn primitives, deep boolean trees, extrudes over many-vertex profiles, comprehension-driven polyhedra) with value-only statements suppressed as timing noise — but it is emitted by walking a surface declaration rather than by a bespoke match. RESCOPED from "hardcode a geometry grammar" because `const BUILTINS: &[(&str, usize)]` IS already a surface, just an impoverished one: upgrade it to carry per-parameter NAMES (so named-arg calls are generatable — that is where AN.14's whole diagnostic family lives, and a positional-only corpus cannot reach it) and DOMAINS (number/vector/path/VNF/region/bool). Builtins become surface #1; a transpiled library implementing AR.3's trait is surface #2 with NO new generation machinery. Hardcoding instead means writing the call generator twice
- [x] AO.3 - Blowup guards for the heavy lane: hard cap on minkowski/hull nesting + per-seed oracle timeout + Config::eval_budget set, so one seed can't eat the nightly
- [x] AO.4 - Kill the startup confound: scale the dial until oracle wall time is >=1s (55ms fork drops under 5%), and report RAW alongside startup-adjusted instead of only the adjusted median that saturated to 0 in AK.2
- [x] AO.5 - Cold-render discipline: fab timings run on a FRESH SolidStore / FAB_CSG_CACHE=0 (the W.3.17 cache-warm trap — generated seeds repeat shapes, so a warm cache measures re-renders not renders)
- [x] AO.6 - Correctness gates the timing: a timed seed must first AGREE with the oracle (echo + geometry residual, viable now that S.4 closed) — a fast wrong answer scores nothing
- [x] AO.7 - Publish a SCALING CURVE (time vs complexity dial), not a single median — shows where we win/lose asymptotically; lands with K.4's per-run artifacts next to the divergence trend
- [x] AO.8 - Wire the heavy lane into nightly sustainment beside gen-diff (AL.2) on its own slower cadence; keep it distinct from the REAL-model perf (perf/baseline.json, L.5.6) — generated buys unbiased shape coverage + scaling, real models buy representativeness
- [ ] AO.9 - Nightly fuzz budget as ONE knob, targeting ~1h TOTAL job time (chotchki). Today the workflow carries NINE independent `-max_total_time` numbers summing to 2100s/35min that nobody tracks, so "make it an hour" is a nine-file edit and the sum is never checked. Replace with a single `FUZZ_BUDGET_S` env var plus a documented per-target share (shell arithmetic in each step), so the allocation is visible and one number moves it. NOTE the budget covers FUZZING only — job wall time also pays the ASan build, the BOSL2 corpus seeding and the `cmin` minimize pass, so the knob must be calibrated against a REAL run rather than computed: set it, read the actual job duration, adjust. Also switch the AO heavy lane from a fixed seed count to a WALL-CLOCK budget (chotchki: "okay if that becomes a runtime cap instead of a fixed N runs") — heavy seeds have wildly variable cost, so a seed count buys an unpredictable runtime, which is the wrong contract for a nightly
- [x] AO.10 - Assert a timed seed DID REAL WORK before its number counts — the AR.4 trap, made executable. A call with wrong-typed arguments returns `undef` in ~0 time, so a corpus that degrades into failing calls looks FASTER while measuring nothing; worse, a regression in call-generation quality would report as a performance WIN. So gate every timed seed on a work floor (vert/tri count, or Config eval_steps, over a threshold) and report the REJECTED fraction alongside the timings — a rising reject rate is the signal that the surface's domains have drifted out of usefulness. Distinct from AO.6, which gates on AGREEING with the oracle: a seed can agree perfectly and still have done nothing, because both engines produce nothing equally fast
- [x] AO.11 - Upstream crash: search() aborts OpenSCAD on a non-string table column
- [x] AO.12 - AO.2 is the BLOCKER for a meaningful ratio — the dial grows text, not geometry
- [x] AO.13 - Triage the ~70 echo divergences the heavy lane surfaced
- [ ] AO.14 - RETRACTED then re-measured: fab leads 2.6-10.7x, and the lead GROWS with size
- [ ] AO.15 - Make the measured ENGINE impossible to get wrong
## Phase AR - Build-time library transpiler (replaces intrinsics AND the JIT) - DIRECTION, post-AO
- [x] AR.0 - AR.0 — the eval-share ceiling, and the go/no-go rule stated in advance
- [ ] AR.1 - DIRECTION (chotchki). SUCCESS CRITERION SETTLED 2026-07-28: the transpiler is a MAINTENANCE bet, NOT a performance one — "I'm not seeking performance wins from the transpiler but rather maintenance wins". Judge it on deleted hand-written surface, not on ms. The earlier framing weighed a speed case and warned it might hit the L.4 wall (the JIT was 34-334x per CALL and still net-neutral on real geometry because geometry dominates); that warning is now MOOT rather than sobering, because speed was never the bar. Measured for the record at AR.2, frame_upper.scad: the ~55 natives are worth ~37% of the EVAL tier but only ~8% of wall time. END STATE, also chotchki's call: once the transpiler is live and proving out, BOTH the JIT and the intrinsics get REMOVED. That makes AR.2's retargeted acceptance suite the load-bearing deliverable — with both hand-written tiers gone, those differentials are the only thing between the transpiler and a silent wrong answer. Keep (a) one tier everywhere INCLUDING wasm as a real benefit, since the browser cannot JIT in-sandbox
- [x] AR.2 - The AN guard findings are the transpiler's SPEC. First deliverable, found by tracing the JIT's acceptance suite: a `Config::intrinsics` RUN GATE. jit_dispatch_diff exists because a positional-binding harness structurally cannot catch the AN binding family — it toggles Config::jit and diffs the whole console through the real call machinery. The transpiled natives have no equivalent and CANNOT get one: Config has jit/eval_cache/csg_cache/eval_budget but no way to turn intrinsics OFF, so there is no interpreter oracle to diff against. Gate first, then intrinsics_dispatch_diff is a near-copy. Also a hard prerequisite for AR.1
- [x] AR.3 - A LIBRARY SURFACE trait — the thing the advanced fuzzer generates calls against, and the transpiler's output contract (chotchki). Today the generator picks from a hardcoded `const BUILTINS: &[(&str, usize)]` (name + arity), which cannot describe a real library and so cannot fuzz one. Needed instead: a trait a transpiled library implements, declaring the functions/modules it hosts with, per parameter, its NAME (so named-arg calls are generatable, which is where AN.14's whole diagnostic family lives) and a DOMAIN. Note `intrinsics::Entry {name, reference, consts, consts_v, deps, builtins, func}` is ALREADY a hand-maintained surface manifest of exactly this kind — the transpiler should GENERATE that description rather than have it hand-written, and the fuzzer consumes the same one. Three consumers, one declaration: the advanced fuzzer (AO), transpiled-library fuzzing (AR.1), and the intrinsic/transpiled dispatch registry itself
  - [x] AR.3.1 - the SEAM + the derived declaration: a `Surface` trait in fab-gen (decls + preamble), a `Builtins` impl byte-for-byte identical to today's table, and `NativeSurface::from_registry` built from `fab_lang::native_surface()` — names and required-ness PARSED from each entry's `reference`, the same verbatim source the fingerprint gate checks, so the surface cannot drift from what actually dispatches. Seed stability is part of the contract and is tested: pick_builtin indexes the surface with the RNG, so a reordering would silently re-point every accumulated fuzz corpus at different programs
  - [x] AR.3.2 - GENERATE against a surface — `generate_against(seed, profile, &dyn Surface)` threads the chosen surface through Gen and emits its preamble BEFORE any RNG draw, so `Builtins` output is byte-identical to the pre-refactor binary (verified against the 18:02 build: seeds 0/7/42/1337 all identical, corpora keep their meaning). A separate entry point on purpose: a seed means something different under a different surface, since the RNG indexes the decl table
  - [x] AR.3.3 - DOMAINS are DERIVED too — a defensive library declares its own types. Read off the predicates each reference applies to its own arguments (is_vector 27x, is_list 21x, is_num 13x, len 48x across 58 references), as a SET not a winner: approx tests is_bool AND is_num AND is_list on one parameter, so collapsing picks a branch the source never chose. Coverage 16% -> 55% once assert/let/comprehensions were walked, which is where BOSL2 actually states types — and that is now an ASSERTED FLOOR, because a walker that stops seeing a node type does not error, it just quietly goes back to feeding natives untyped arguments while still passing. Verified reaching the generated call: v_theta([17, 7.2, -11, 32.0]) under the heavy profile
- [x] AR.4 - DOMAINS are load-bearing for a PERFORMANCE fuzzer, not a nicety — the trap AO.2 must design around. A generated call whose argument types are wrong returns `undef` almost immediately: it costs nothing, renders nothing, and times as ~0. So a surface carrying only (name, arity) produces a corpus that measures ERROR HANDLING while looking like it measures geometry — the failure is invisible, because the programs still run, still agree with the oracle, and still report a ratio. That is the same shape as today's blind-channel bugs: not wrong, unfalsifiable. The surface therefore needs enough type information (number / vector / path / VNF / region / bool) to generate calls that actually DO work, and the heavy lane needs a guard asserting that a timed seed produced non-trivial geometry (vert/tri count over a floor, or eval steps over a floor) rather than trusting that it did. Without that guard a regression in call-generation quality reads as a performance WIN, since failing calls get faster

- [x] AR.11 - The BOSL2 coverage report as a durable trend line — 47.3% of 1335 functions ALREADY emit. Run the v0 codegen over every top-level function in the pinned BOSL2 and histogram the DECLINES, because a decline names the construct the emitter does not own and the histogram is therefore the roadmap in priority order. Not a vanity metric: it is the same asserted-FLOOR shape as AR.3.3's domain coverage, for the same reason — an emitter that silently stops handling a construct does not error, it just quietly falls back to interpretation while every test still passes, so the number has to be a gate or it is worthless. Note the histogram is FIRST-DECLINE-WINS, which makes every band a LOWER bound (a function that trips on a free read may also hold three strings)
- [x] AR.12 - The transpiler's INPUT becomes the LIBRARY, not the hand registry. Today `generate_module` takes `&[&str]` of REGISTRY entry names and reads each one's hand-maintained `Entry.reference` — the transpiler cannot see a library at all, only the 55 functions somebody already typed out. Replace with a library READ: parse the `.scad` tree, build the symbol table (functions AND top-level constants), derive the guard sets library-wide from the same parse. This is the item that makes "a crate per lib" mean anything, and it is what finally kills `bake_entry`'s dependence on hand-written `Entry.consts`/`consts_v`. LANDED: 1329 functions + 128 constants read from the pinned BOSL2, with EQUIVALENCE to the old input proven — all 52 registry entries that BOSL2 declares fingerprint-match their transcribed reference, 0 drifted (the other 7 are our own POCs). Two things fell out that the hand input structurally could not show. COLLISIONS: BOSL2 declares three names TWICE at column 0 in one file (`_sort_vectors` — the known last-wins trap that already cost a bug — plus `_get_cp` and `_list_shape_recurse`, both same-arity, so almost certainly upstream dead code). A colliding name is REFUSED rather than resolved, because which body a user gets depends on their include graph and not on ours. And an ANALYZER BUG: a C-style comprehension's update clause BINDS, it does not only reassign, so `_dp_distance_array`'s `newrow` was being reported as a free global read — 19 phantom free names collapsed to 6 once update walked as bindings. No hand reference uses that form, which is exactly why 55 transcribed functions could never have surfaced it
  - [x] AR.12.1 - Root reads + PROVENANCE — a library is an include closure, not a directory. AR.12 shipped a directory glob, which describes a program NOBODY HAS: `std.scad` reaches 30 of BOSL2's 56 files and gears/screws/threading/nurbs are opt-in roots a user includes separately. Split out rather than folded into AR.12 because it is new scope from chotchki's `fab_transpile!(["BOSL2/std.scad"])` shape, and the box was already ticked. MEASURED: std.scad's closure is 934 functions / 106 constants / 32 files against the directory's 1329 / 169 / 56. The closures COMPOSE rather than nest — `gears.scad` has no includes at all, it assumes std is already there — which is exactly why the macro takes an array. `include` vs `use` is honored (use imports modules and functions, NOT variables); getting that backwards would let AR.16 bake a value the consumer's program never binds, so the native answers with a number where the interpreter says undef. PROVENANCE per chotchki — "the registry needs to know what root emitted what, so when a downstream consumer includes it, it gets what it asked for, which make include more than just itself": each root keeps its OWN closure keyed by the path a consumer writes, because the answer is wrong in BOTH directions without it (a program including only std.scad must not be told it may call `spur_gear`, and one restricted to std.scad's own declarations misses 934 functions). A missing function costs a silently-absent PART, not an error. Also made a missing or empty root a LOUD error: a typo'd path previously read as a successful transpile of a library declaring nothing
- [x] AR.13 - `fab_lang::rt` — the emission target becomes a NAMED public surface. Generated code today reaches `crate::eval::{ops, builtins, build_vector, iter_values_native, build_range}` and `super::{bosl_assert, native_rt}`, all `pub(crate)`/`pub(super)`, which works ONLY because generated.rs is eval's own descendant. Moving it to another crate forces every one of those to be published — and that is a benefit, not a tax: today the emitter may reach anything in fab-lang, and after this it may reach exactly what `rt` names. Audited 2026-07-28 and the ABI is small and clean (~12 items, all pure value algebra with no evaluator context to thread), so the topology risk chotchki is taking here is LOW. `#[doc(hidden)]` with a stability note: this is the transpiler's ABI, not a user API
- [ ] AR.14 - THE CRATE SPLIT: fab-lib (transpiler) + fab-lib-bosl2 (generated), and the dependency INVERSION that makes it possible. The constraint: fab-lib-bosl2 depends on fab-lang for the runtime, so fab-lang CANNOT depend on fab-lib-bosl2, so `intrinsics::REGISTRY` — a static inside fab-lang that dispatch consults directly — has no home in the new topology. SHAPE SETTLED 2026-07-28 (chotchki), and it is bigger than the inversion I proposed: "the fab-lib-bosl2 library should be exporting the implementation of a library surface trait that includes constants/functions/modules, that trait is what the fuzzer/fab-gui/etc should be consuming. I think its reasonable for those modules to be expect to be given a registry of loaded stuff that keeps getting built up". So the answer to the registry question is neither of the two I offered — not a threaded `Config` and not an install-once global, but an ACCUMULATING registry the consumer builds up and passes in. That is the better answer for a reason I had not weighed: it composes. BOSL2 plus machineblocks plus a user's own library is the normal case, not the exception, and both of my options quietly assumed exactly one library. It also kills the global-init ordering hazard outright rather than documenting around it. AND the three overlapping declarations collapse into ONE: `fab_gen::Decl` (the fuzzer's view, already carrying `Kind::{Function,Module}`), `fab_lang::SurfaceFn` (derived from references at runtime, then LEAKED to get `'static`), and `intrinsics::Entry` (the dispatch view) are three descriptions of the same thing maintained separately. One trait in fab-lang — every crate already depends on it — with constants, functions and modules on it, implemented by the generated crate as STATIC data. The runtime derivation and its leak both disappear, because a generated library declares itself at build time instead of being read back at startup. NOTE what declaring modules buys BEFORE any module is transpiled: the fuzzer can generate calls against BOSL2's 416-module surface as soon as it is declared, which is coverage AR.20's transpiling question does not gate
  - [x] AR.14.1 - The unified `LibrarySurface` trait in fab-lang — constants, functions AND modules, one declaration. Lives in fab-lang because everything already depends on it (fab-gen, fab-lib-bosl2, fab-gui) and a GENERATED library crate must not depend on the fuzzer to describe itself. Two lists, not one with an `Option`: `callables()` is pure DECLARATION (name, kind, params with names + domains + required-ness — what the fuzzer and any doc consumer need) and `natives()` is IMPLEMENTATION (reference, fingerprint, guard sets, fn pointer). They are deliberately different lengths — BOSL2 declares 1335 functions and we compile 742 — and folding them into one list with an optional fn would assert they are the same set, which is exactly the drift the phase exists to kill. `Builtins` implements it with no constants and no natives. Plus `roots()` carrying AR.12.1's PROVENANCE, so a consumer that includes one root is told what that root declares and not what happened to be read alongside it. LANDED with the declaration types MOVED VERBATIM out of fab-gen rather than merged: `fab_gen::Domain` (generation policy — Pos/Unit/Deg) and `SurfaceDomain` (derived evidence — Indexable/Vector) overlap but are not the same vocabulary, and merging them is a behavioral change to the generator. Deferred to AR.14.5 so THIS step's seed stability is trivially provable. And it was proven, not assumed: built the pre-refactor binary from 4f49c264 in a throwaway worktree and diffed seeds 0/7/42/1337/99991 — all byte-identical. Then made that a GATE (`seeds_still_generate_the_same_bytes`), because the existing determinism test compares a run against ITSELF and so cannot see a refactor that re-points every seed at a different program: `pick_builtin` indexes the surface with the RNG, so any change to the decl table's contents or order silently invalidates every accumulated fuzz corpus while the seeds still generate, still label and still report a ratio. Verified the gate discriminates (one byte of pinned length fails it)
  - [x] AR.14.2 - The registry becomes a KEYED, TYPED structure — the lookup stops being a linear scan. chotchki: "sounds like table needs to be a map/tree so its easier to cross link and its going to want to reference itself" — not conflating anything, `table()` IS the registry's index, just stored as a Vec and scanned by name. MEASURED shape: 59 entries, 259 dep edges, avg 4.4 deps each. Every access is a linear name scan (`resolve`, `entry_by_name`, `anchor_fp`, `classify`), and `guard_veto` calls `anchor_fp` once PER DEP PER candidate entry, so arming is O(defined x deps x registry). Invisible at 59; at 742 natives it is a few million string compares per evaluation. THE CROSS-LINKS MUST STAY BY NAME, and that is not laziness — the dep graph has REAL CYCLES (4 of them: approx<->idx, approx<->posmod, all_nonzero<->is_vector, and the approx/idx/posmod 3-cycle), and a cyclic graph of `&'static` references cannot be built in safe Rust. Multi-library composition says the same thing from the other side: a global index space does not exist until the registry is assembled, so a cross-library link has to be a name. So the fix is the LOOKUP, not the linkage: map/tree keyed by name and by (name, fingerprint). STRONGER TYPING is the other half, per chotchki, and this is where it earns its keep: today `anchor_fp(&str)` / `entry_by_name(&str)` / `resolve(&str, ..)` all take a bare `&str`, a fingerprint is a bare `u64`, and `deps: &[&str]` is untyped linkage — nothing stops a hash being passed where a fingerprint belongs, or a module name where a function name belongs. Newtype them (`Fingerprint`, `LibId`, the name key) so the compiler checks the graph instead of the reader LANDED: `table()`/`pin_table()` are `BTreeMap`s keyed by name, and all six lookups (`resolve`, `entry_by_name`, `anchor_fp`, `reference_fp`, `matrix_targets`, `classify`) are hits rather than scans. `Fingerprint(u64)` is a newtype — it propagated to nine sites and the compiler found every one, which is the argument for it: that value is the ENTIRE basis on which a native may stand in for a library function, and it travelled as a bare u64 through lookups that also carry ordinary u64s. Three tests pin what the index changed: the index AGREES with the linear scan it replaced (re-derived the slow way, name for name — verified it fails when the index drops one), names are UNIQUE across REGISTRY and PINS (a duplicate silently loses an entry, and the map is keyed by name so it would answer with the survivor), and the dep-graph CYCLES are asserted so the next person tempted to swap names for pointers finds the reason it is impossible rather than discovering it
  - [ ] AR.14.2a - Pass the registry in and accumulate it — the Config-level inversion, split out of AR.14.2 because the keyed/typed structure is self-contained and provable on its own while the plumbing reaches every dispatch site. Consumers add libraries as they load them and hand the registry to evaluation; `Config::intrinsics` stays as the per-eval toggle, since AR.2's differential must turn natives OFF without changing which libraries are PRESENT. The hard part is that `table()`'s process-lifetime `OnceLock` is keyed on nothing, which is sound only while exactly one immutable registry exists per process — the assumption an accumulating registry exists to break
  - [ ] AR.14.3 - fab-lib: the transpiler moves out of fab-lang into its own crate. `eval/transpile.rs` + `eval/library.rs` are already a self-contained pair — analysis, codegen, library read — that only fab-lang's TESTS consume. Moving them is mostly mechanical now that AR.13 named the ABI; what it buys is that fab-lang stops shipping a code generator to every consumer that only wants to evaluate
  - [ ] AR.14.4 - fab-lib-bosl2: the generated crate, and its surface emitted as STATIC data. DELIVERY SETTLED 2026-07-28 (chotchki): "I'm kinda expecting fab-lib-bosl2 to be a huge proc macro when all is said and done", same for machineblocks. That is the right end state and it costs nothing to keep open, PROVIDED fab-lib stays a pure function from library-source to Rust-source with no opinion on delivery — then checked-in generation and a proc macro are the same transpiler with a different consumer, and switching is not a rewrite. So: ship CHECKED-IN first (one module per upstream .scad, reviewable, no build-time transpiler dep) and convert once the emitter stops moving. AR.13's `extern crate self as fab_lang` already makes the emitted text identical either way. THE OBJECTION I WOULD HAVE RAISED IS ALREADY ANSWERED: a checked-in artifact gives a reviewable diff when BOSL2 bumps, and a macro does not — but the diff worth reviewing is the SUBMODULE's, and the regression that actually matters (functions falling out of coverage) is caught by AR.11's ratchet, which is a test rather than an artifact. So reviewability does not gate this. WHAT DOES gate it, and must be MEASURED not argued: expansion cost. Parsing 85K lines of OpenSCAD and handing rustc ~1.7 MB of generated tokens would run on every clean build of every consumer — fab-scad, fab-gui, the wasm bundle, CI — where checked-in output costs only the rustc half. Measure the emit+compile time at full coverage before converting. Second wrinkle: proc macros are not rebuilt when a file they read changes unless the file is `include_str!`d, so the macro needs an EXPLICIT list of the 56 .scad files rather than a glob — which is fine, and arguably better, since a silently-dropped library file is the AH-family failure where a missing input costs a part and not an error
  - [ ] AR.14.5 - fab-gen consumes the unified trait — the third declaration dies, and the leak with it. `NativeSurface::from_registry` derives decls at runtime and `Box::leak`s them to satisfy `&'static [Decl]`; against a generated library the decls ARE static and the leak is simply deleted. Seed stability is the acceptance test, same as AR.3.2: `Builtins` output must stay byte-identical or every accumulated fuzz corpus silently re-points at different programs
- [x] AR.15 - String literals — the cheapest band, 203 functions. `Value::Str` is simply not emittable today, which is why `str_find`, most of attachments.scad's anchor plumbing, and every function with a `style="default"` parameter declines. - [ ] AR.16 - Library constants baked from the library's OWN top level — 375 functions, the biggest single band. Every one of these declines on a free read of `_EPSILON`/`UP`/`CENTER`/`_NO_ARG`/`INF` — names the hand registry supplies through `Entry.consts`/`consts_v` one at a time and the library supplies for free now that AR.12 can see it. WORK LIST MEASURED at AR.12, ranked: `_EPSILON` 131 functions, `UP` 106, `CENTER` 70, `_NO_ARG` 43, `BACK` 34, `RIGHT` 29, `INF` 27, then a tail. The const-GUARD contract carries over unchanged and must: the fingerprint proves the FUNCTION, never the constants it names, so a user's `_EPSILON = 1e-6;` still has to disarm every native that baked the old value. TWO complications AR.12 surfaced. (a) `PI` is read by 31 functions and the LIBRARY does not declare it — it is a seeded builtin, so the bake source is the interpreter's own seeding, not the library read. (b) Five functions read names NOTHING declares (`gear_shorten_skew` reads `helical` while declaring `helical1`/`helical2` — an upstream bug that silently returns undef), and those still need a guard rather than a bake, because a user CAN define the missing name at top level and change what the function means. Bakeable-vs-not is 22 names vs 6, so the ceiling this band leaves behind is negligible
- [ ] AR.17 - First-class functions: computed callee + function literal (~92 functions, fnliterals.scad is the whole file). Three related declines — computed callee 73, function literal 19, call-through-a-local-binding 18 (the AN.10 shape, which the analyzer already reasons about correctly for GUARDS but the emitter cannot compile). Real language work rather than a mechanical band, and the first place where the emitter needs a value that is not a `Value` in the ordinary sense
- [ ] AR.18 - The residual bands: non-contiguous named args (49), C-style comprehension (9), echo (4). The named-arg one is the interesting one and is NOT a syntax gap: the native ABI is a positional `&[Value]` slice, so a sibling call that fills args 0 and 3 has nowhere to say "and nothing in 1 or 2" — filling the holes with `Value::Undef` is WRONG because an unfilled slot evaluates its DEFAULT in the lexical base while an explicit undef does not, which is the AN family's exact failure mode. Either widen the ABI or decline honestly
- [ ] AR.19 - Dispatch at LIBRARY scale — arming 1000+ entries cannot be 55 entries' algorithm run 20x. `arm_guarded_intrinsics` walks each entry's transitive dep closure against the island globals at arm time; that is fine at 55 and quadratic-ish at 1300. The transpiler knows the whole symbol table at BUILD time, so the closure should be precomputed into the generated crate and arming should reduce to a set intersection. Correctness is unchanged and must be PROVEN unchanged (same wire-only-if-proven contract); this is purely about not paying a startup tax for the privilege of deleting hand-written code. SECOND scaling trap, found reading `native_rt` at AR.12 rather than by hitting it: AR.10's decline-to-interpreter path interprets a `FALLBACK_SOURCES` string holding the whole batch's verbatim references, and `run_interpreted` caches that parse per THREAD keyed on the string's (ptr, len). At 14 functions the string is 4 KB and nobody notices. At library scale it is all 85K lines of BOSL2, so the first depth-exceeded call on each worker thread pays a full library parse and every thread then holds its own copy of the AST. Three ways out and they are not equivalent — split FALLBACK_SOURCES per generated module (bounded, but a declining function's deps can live in another file), share one parse across threads behind a lock (contention on the exact path that is already the slow one), or drop the embedded copy entirely and interpret against the USER's island (free, but it gives up AR.10's guarantee that the interpreted bindings equal the bakes bit-for-bit, which is the whole reason the copy is embedded)
