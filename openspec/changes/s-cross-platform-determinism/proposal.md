# Phase S - Cross-platform determinism (J.4.5): Manifold parallel determinism holds same-platform; verify cross-platform, then re-baseline

## Why

SPEC.md's Engine determinism rule (the "doctrine #36" the boxes cite) promises bit-identical output on every run and every platform we ship, and J.4.5 found the native build could not back that promise: Manifold ran TBB-parallel on native and serial in wasm. Phase S checks the promise one axis at a time, run-to-run (S.1, S.4), parallel vs serial (S.2) and native vs wasm (S.3), and re-baselines whatever fails.

## What Changes

- Shipped: S.1, S.2 and S.4. S.1 and S.2 ran against the C++ kernel (`MANIFOLD_PAR` is its build switch), and their runs exist only as box text: Phase S first enters git at `4ef936ff` (2026-07-12) with both already ticked, and no commit message records the runs. `docs/tbb-backend-spike.md:17` (W.3.9) backs S.2's conclusion independently, from the C++ source. S.4 landed in `17274a94` + `56a0dbf1` (2026-07-19): `Solid::components()` sorts on a total order (`src/kernel.rs:900-928`), and `tests/determinism_render.rs` is the standing run-to-run guard, green on macos-latest in the v1.4.0 CI run (35548486189, 164 s).
- S.1 and S.2 are ticked but describe a kernel that no longer ships. M.7.4 cut the C++ (`7f98be4f`, 2026-07-16), and their pure-Rust successors prove more: M.4.4's seq==par byte golden (`6d8153cd`, `boolean_pipeline_bytes_match_golden`) and M.6's 33-case fingerprint table (`manifold/tests/m6_native_wasm_golden.rs`), which held on native-serial, native-par and wasm32-wasip1 under wasmtime at `f9582ba7` and again at M.7.4. Its last regen (`5876ccef`) records serial == par only, so no wasip1 run is on record for the current table. The title's "re-baseline" went the same way: J.4.5 meant re-baselining after forcing native to serial, and par ≡ serial by construction removed the need. No box tracks it and nothing is owed.
- S.3 (OPEN): its premise is stale. A wasm mesh harness exists at two levels. The kernel's golden table runs under wasmtime (`4df26682`, the `.cargo/config.toml` runner), and SZ.9.3 (`95845049`, 2026-08-03) built the end-to-end check: `packaging/web/e2e-web-native-parity.sh` renders `e2e-parity-model.scad` (BOSL2 `cuboid` rounding plus three `cyl`s at `$fn=32`) in headless Chrome, and `src/bin/mesh_diff.rs` diffs the result against a desktop render of the SAME request. It reports 558 vs 558 tris, relative volume difference 0e0 and MATCH at eps 1e-6, on every push (`ci.yml` boot-gate) and every web release (`release-web.yml`), and it was green for v1.4.0. Three gaps remain, and only the first is S.3's own ask: the CI leg is x86_64 Linux (glibc), never the arm64 macOS or x86_64 Windows natives we ship, and the only arm64 end-to-end run is one local run claimed in `95845049`'s message (architecture unstated; the kernel goldens do run on arm64 macos-latest every push); it is a 1e-6 tolerance check on one fixture, not bit-for-bit; and the kernel's wasip1 leg runs by hand only, since no workflow names wasip1.
- The mechanism S.3 predicts is present; a divergence has never been measured. fab-lang tessellates through `sin_degrees`/`cos_degrees` (`lang/src/eval/geometry.rs:20`), which fall back to std `f64::sin`/`cos` on any non-snapped angle (`lang/src/eval/trig.rs:104-123` and `:178-202`). `lang/Cargo.toml` has no `libm` dep, and `lang/clippy.toml` bans no transcendental, unlike `manifold/clippy.toml`. L.2.8i measured macOS libm 2 ULP off on `acos(-0.5)` and found musl `libm` "ALSO off, differently". The one cross-target data point (SZ.9.3, non-snapped `$fn=32` angles) matched at relative volume 0e0, but a 1e-6 check can't see an ulp, so whether a bit-exact diff shows one is unverified. The box's fix (the `libm` crate in fab-lang) has a cost it doesn't name: native≡wasm bits, but no longer matching same-platform OpenSCAD on non-nice inputs (see External). L.2.8i left those on platform libm and snapped only nice angles (generalized in `d4dac6bf`), a snap the swap doesn't touch.
- S.4's text has drifted in three places. It says rayon is "clippy-banned outside par.rs", but neither clippy.toml (`lang/`, `manifold/`) mentions rayon and none ever did (`git log --all -S rayon -- '*clippy.toml'` is empty). Within the kernel, rayon's iterators sit only in `manifold/src/par.rs` by convention, and the root crate has two more doors: `decimate_parts` (`src/decimate.rs:506`, an index-order collect, so it is safe) and the `render --all` sweep (`src/main.rs:960`, which only prints pass/fail). The box also lists four models verified while the guard holds two (garage_door, window_light_blocker); pill_holder and ashtray were a one-time run. Finally, the guard SKIPs rather than fails when a model is absent or fails to resolve, so a green run does not say which models actually rendered.
- S then reduces to S.3, and S.3 needs a decision before any work. One path ticks it on SZ.9.3 + M.6 and files the evaluator's residual libm divergence to backlog. The other rescopes it to a bit-exact arm64-vs-wasm check of fab-lang's tessellation (fingerprints under wasmtime the way M.6 does it; whether fab-lang builds for wasm32-wasip1 is unverified, and its ungated `proptest` dev-dep is the blocker `4df26682` had to target-gate for fab-manifold), plus the libm-vs-oracle call above.

## Impact

- Every std transcendental in fab-lang, which a fix would reroute: `lang/src/eval/trig.rs`, `builtins.rs` (ln/log10/exp/pow), `ops.rs` (`^`), `dxfdim.rs` (hypot) and `lang/src/geom.rs` (acos). If that path is chosen, `lang/Cargo.toml` takes a `libm` dep and `lang/clippy.toml` a transcendental ban, the seam-plus-ban of `manifold/src/mathf.rs` + `manifold/clippy.toml` (though mathf transliterates `math.h`, keeping `libm` only for `remquo`); `manifold/src/par.rs` and `src/kernel.rs` (`Solid::components`) for S.4.
- Harnesses: `packaging/web/e2e-web-native-parity.sh` + `e2e-parity-model.scad`, `src/bin/mesh_diff.rs`, and `.cargo/config.toml` (wasip1 → wasmtime). The parity gate runs in `.github/workflows/ci.yml` (boot-gate, ubuntu-latest) and `release-web.yml`; nothing runs wasip1.
- Tests: `tests/determinism_render.rs` (needs the public `models` submodule, which CI checks out), `manifold/tests/m6_native_wasm_golden.rs` (native leg in the workspace run, wasm leg by hand), `boolean_pipeline_bytes_match_golden` (`manifold/src/boolean/boolean_result.rs:1492`). Despite its name, `tests/web_native_parity.rs` does not check geometry (SZ.1: both render doors arm the same natives).
- Source of truth: SPEC.md "Determinism doctrine" (line 222, Engine determinism at 234) owns the promise; SPEC_manifold-rs.md Pillars 1 and 2 (lines 65, 90) own the kernel's par and libm seams; `docs/web-embed.md:231` describes the parity gate. `README.md:93-94` says "a byte-golden suite holds native≡wasm": true for the kernel only, and only when someone runs the wasip1 leg.
- Release reach: everything shipped under S is test- or CI-only except S.4's `Solid::components()` sort hardening (`src/kernel.rs`, on the slice path), product code since web-v0.19.0 and output-neutral on real models. A fab-lang libm switch would ship: renders could move an ulp on non-snapped angles in the next v* tag (macOS dmg/.app, Windows installer and web bundle on one release, latest.json to the macOS auto-updater), and hotchkiss.io's `/3d` editor picks that up only when its own build.rs pin moves. The next release can reverse it, so there's no one-way door, and the updater key isn't involved.
- External: the OpenSCAD oracle calls its platform's libm, so whichever libm fab-lang uses decides which platform's OpenSCAD it matches bit-for-bit on non-nice angles (L.2.8i). The BOSL2 pin is unaffected.
